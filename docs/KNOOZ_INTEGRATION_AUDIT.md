# تدقيق تكامل منظومة الشركات — App / Web / Admin

تاريخ: 2026-11-10

## العلاقة بين الأنظمة

```text
Admin Panel ── يدير ──► companies / company_users / roles / status / packages
        │
        ▼
   Laravel Backend (نفس DB)
        │
        ├── Session guard `company` ──► لوحة تحكم الشركات (Web)
        └── PanelApiToken panel=company ──► تطبيق Flutter الشركات
```

التطبيق والويب ليسا نظامين منفصلين؛ كلاهما يستهلك نفس جداول الشركة ونفس المستخدمين.

## تطابق الحسابات

| البند | الحالة |
|---|---|
| نفس نموذج `CompanyUser` | نعم |
| نفس بيانات الدخول (بريد/جوال + كلمة مرور) | نعم — حقل `login` في API |
| حساب بذرة موحّد | `company@knooz.test` / `password` (جوال `0553333333`) |
| جداول مستخدمين جديدة للتطبيق | لا |
| نوع التوكن | `PanelApiToken` مع `panel=company` (منفصل عن توكن المركز) |

## تطابق الصلاحيات والحالة

| السيناريو | السلوك |
|---|---|
| شركة Inactive / Suspended | رفض Login + قطع الطلبات المحمية |
| مستخدم Inactive | رفض Login / قطع الجلسة |
| توكن مركز على مسار شركة | 403 |
| الوصول لمركبات/عمليات شركة أخرى | مرفوض (عزل `company_id`) |
| صلاحيات دقيقة على مستوى أزرار الويب | التطبيق يعرض وظائف القراءة المتاحة للشركة؛ لا يوجد نظام صلاحيات مستقل في Flutter |

ملاحظة: لوحة الويب تعتمد جلسات و middleware لوحة الشركات؛ التطبيق يعتمد `panel.api` + `company.api`. النتيجة الأمنية متكافئة لعزل المستأجر، مع اختلاف آلية الجلسة (Session vs Bearer).

## تطابق البيانات

| المصدر | الويب | التطبيق |
|---|---|---|
| بيانات الشركة | Views + DashboardService | `/dashboard`, `/auth/me` |
| المركبات | Company Vehicle controllers | `/vehicles` |
| العمليات | قائمة العمليات للشركة | `/operations` + recent في dashboard |
| المحفظة | عرض الرصيد | `/wallet` |
| الفواتير | صفحات الفواتير | `/invoices` |
| الاشتراك | بطاقة الاشتراك | `/subscriptions` + stats |

تحديث الملف الشخصي من التطبيق يكتب على نفس سجل `company_users`.

## سلامة تدفق العمليات

1. Admin يوقف شركة → Login التطبيق والويب يفشلان حسب سياسة الحالة.
2. تعديل اسم الشركة من Admin → يظهر في `me`/`dashboard` وفي الويب.
3. عملية خدمة تُسجَّل على مركبة الشركة → تظهر في عمليات التطبيق والويب ولوحة الإدارة حسب نطاق العرض.
4. Logout التطبيق يبطل التوكن؛ الويب يستخدم جلسة منفصلة (تسجيل الخروج من أحدهما لا يغلق الآخر تلقائياً — سلوك متوقع لتعدد القنوات).

## نقاط اختلاف / مخاطر

| النقطة | المخاطر | التخفيف الحالي |
|---|---|---|
| شحن المحفظة / إضافة مركبة في Figma بدون API كتابة | فجوة UX | زر الإضافة يوجّه لرسالة «متاح عبر لوحة الويب»؛ لا mock |
| حدود ميزانية لكل مركبة في التصميم | غير موجودة في DB/API | شريط الإنفاق لكل مركبة غير معروض |
| صلاحيات granular per-user داخل الشركة | إن وُجدت في الويب فقط جزئياً | الحماية الأساسية: عضوية الشركة + حالة الحساب |
| جلسات متوازية Web+App | متوقع | توكنات منفصلة؛ إبطال عند تعطيل الحساب |
| cleartext HTTP للتطوير | غير مناسب للإنتاج | HTTPS مطلوب قبل الإطلاق |

## الخلاصة

التكامل المعماري سليم: حساب واحد، بيانات واحدة، إدارة مركزية عبر Admin، قناة API للموبايل موازية لجلسة الويب دون ازدواجية مستخدمين.

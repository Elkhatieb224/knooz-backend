## 1. قرارات منتج — محسومة (2026-11-10)

| # | الموضوع | القرار المعتمد | أثر |
|---|---|---|---|
| D1 | تطبيق واحد أم اثنان؟ | **تطبيقان منفصلان:** User App ≠ Center App (`flutter/user` و`flutter/center`) | هيكل Flutter والصلاحيات |
| D2 | هوية الموظف المنفّذ + واجهاته | **`center_users` مع أدوار `manager`/`staff`**. عند دخول Staff تظهر واجهات تشغيل منفصلة عن شاشات إدارة المركز. تطبيق موظفي الفروع (المستقل) **خارج النطاق**. FK على operations عبر `created_by_center_user_id` | FK + أدوار + UI |
| D3 | قبول/رفض الحجز | **الأفضل المتاح حالياً:** قبول → `in_progress`، رفض → `cancelled` (+ notes). دون قيم enum جديدة في v1 | Enum + API + UI |
| D4 | خدمات متعددة لكل زيارة | **الأفضل المتاح:** عدة صفوف `operations` لنفس الزيارة (service_id مفرد). pivot لاحقاً إن لزم | DB + شاشة التفاصيل |
| D5 | كود تحقق شركات | **غير مفعّل في v1** — OTP وFCM يُضافان لاحقاً. API يُرجع stub واضح عند الحاجة | DB لاحق + شاشة Identity لاحقاً |
| D6 | هل المركز يفعّل/يعطّل خدماته؟ | **نعم** — `is_available` عبر API services PATCH | API services PATCH |
| D7 | الشكاوى | **الأفضل المتاح:** توسيع `complaints` بـ `center_id` (+ `operation_id` اختياري) | DB + Admin workflow |
| D8 | هل Staff يرى الإيرادات؟ | **لا** — التقارير المالية للمدير فقط | تقارير + أدوار |
| D9 | Forgot password للمركز | **متاح في v1 عبر Email** | Auth API |
| D10 | NFC في v1 | **اختياري مع Manual fallback** (قرار افتراضي عملي) | صلاحيات الجهاز |

### قرارات إضافية محسومة
| الموضوع | القرار |
|---|---|
| الإيرادات المعروضة | **صافي المركز بعد خصم عمولة التطبيق** |
| Walk-in دون حجز | **مسموح دائماً** (إنشاء عملية ميدانية بدون booking) |
| مركز متعاقد vs مملوك | **لا اختلاف وظيفي** سوى عدم إظهار الأرباح للمتعاقد؛ يجب أن يكون واضحاً في لوحة الإدارة للتحكم بهذا الإظهار |

## 2. نواقص Backend مؤكدة

1. لا توجد مجموعة routes `/api/center/...` للموبايل.
2. لا يوجد إنشاء عملية من المسح (QR/NFC/Plate).
3. لا يوجد رفع `operation_images` عبر API.
4. لا يوجد Customers scoped للمركز.
5. `complaints` بلا `center_id` / `operation_id`.
6. لا يوجد حقل/آلية verification code للشركات (مؤجّل — OTP لاحقاً).
7. `center_users` بلا أدوار فرعية (يُضاف `role`).
8. Center Web لا يغطي التدفق الميداني الكامل (مسح/صور) رغم وجود قوائم حالات.

## 3. نواقص/حدود التصميم (Figma)

1. Page 2 مخلوطة بشاشات User App — خطر سحب شاشات خاطئة للتنفيذ.
2. كثير من Frames بأسماء أجهزة لا وظيفية — الاعتماد على Screenshot/نص.
3. حالات Empty/Error/Loading غير مكتملة كـ Frames مستقلة لكل شاشة.
4. تفاصيل شاشة التقارير والعملاء والشكاوى أقل وضوحاً من تدفق العمليات.
5. فصل بصري غير كافٍ بين دور المدير والموظف إن كانا تطبيقاً واحداً — يُعالَج عبر صلاحيات + إخفاء تقارير Staff.

## 4. تعارضات

| التعارض | التفاصيل | الحالة بعد القرار |
|---|---|---|
| info.md vs Figma | تطبيقان وظيفياً في المتطلبات النصية مقابل UI موحّد | **محسوم:** تطبيقان منفصلان User≠Center؛ Staff داخل Center بصلاحيات |
| Booking statuses vs نصوص قبول/رفض | لا توجد قيم accept/reject في enum | **محسوم:** mapping إلى in_progress/cancelled |
| employee_id → users | بينما دخول الويب CenterUser | **محسوم:** `created_by_center_user_id` |
| شكاوى العميل في Admin | ليست شكاوى مركز في التطبيق | **محسوم:** توسيع complaints بـ center_id |

## 5. متطلبات يجب عدم اختراعها دون دليل

- سطحة/وقود/بنشر كتشغيل مركز من نفس Bottom Nav — ظهرت في سياق User App؛ **خارج النطاق**.
- متجر زيوت/إطارات داخل Center App — مستبعد.
- إدارة باقات النظام من تطبيق المركز — مستبعد (Admin).
- تطبيق موظفي الفروع المستقل (طوارئ ميدانية منفصلة) — **مستبعد من Center App**.
- OTP / FCM — **لاحقاً** وليسا في v1.

## 6. توصيات عملية (مطبّقة)

1. تطبيق Flutter منفصل `flutter/center`.
2. P1 API مع D5 stub (verification غير مفعّل).
3. D3 mapping: قبول→`in_progress`، رفض→`cancelled` + notes.
4. طبقة JSON صريحة `/api/center/v1` — لا تعتمد على Blade.
5. `/api/v1` للعميل معزول تماماً.
